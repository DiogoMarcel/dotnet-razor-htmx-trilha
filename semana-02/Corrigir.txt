Q2 — decimal vs double · RESOLVIDO, e melhor que o pedido
------------------------------------------------------------
  "Double utiliza ponto flutuante binário (base 2); Decimal utiliza
  representação decimal (base 10)" — exato, e é o mecanismo, não um sintoma.
  "frações como 0.1 ou 0.2 não possuem representação exata em binário" — exato.

  Rodei o seu exemplo. Ele está numericamente correto, inclusive o valor:

      0.1 + 0.1 + 0.1 == 0.3    -> False
      valor real                -> 0,30000000000000004
      0.1m + 0.1m + 0.1m == 0.3m -> True

  Você não chutou o 0.30000000000000004. Ele confere.

  Detalhe fino, para completar e não para corrigir: 0.1 + 0.1 == 0.2 devolve
  True em double. O erro só aparece na TERCEIRA soma. Isso é o que torna o bug
  traiçoeiro — ele não aparece no teste com dois itens.

  Uma linha para você guardar junto: decimal é a escolha certa para DINHEIRO,
  não em geral. É ~10x mais lento e ocupa 16 bytes contra 8. Em física, gráficos
  ou machine learning, double está certo e decimal está errado.

1. Q6 — IReadOnlyList: você trocou a PALAVRA, não o MODELO.  ** PRIORIDADE 1 **
--------------------------------------------------------------------------------

  Antes:  "o IReadOnlyList<> ADICIONA mais funcionalidades como count e foreach"
  Agora:  "o IReadOnlyList<> CONTEM mais funcionalidades como count e foreach"

  A afirmação continua invertida. E a primeira metade da frase é o erro maior,
  que ficou intacta nas duas versões:

      "Um list<> apenas pode adicionar e remover"

  Isso está errado. List<T> tem Count, indexador [i], foreach, Sort, IndexOf,
  Contains, AddRange, BinarySearch — MAIS Add, Remove, Insert, Clear.
  List<T> tem TUDO que IReadOnlyList<T> tem, e mais.

  A hierarquia real, de menos para mais capacidade:

      IEnumerable<T>                  -> só foreach
        IReadOnlyCollection<T>        -> + Count
          IReadOnlyList<T>            -> + indexador [i]
                                          (fim. não tem mutação.)

      List<T> implementa todas as três acima, MAIS IList<T> e ICollection<T>,
              que é onde vivem Add / Remove / Insert / Clear.

  Então: IReadOnlyList<T> é um SUBCONJUNTO de List<T>. Escolher a interface na
  propriedade é escolher expor MENOS, deliberadamente. O ganho não é
  funcionalidade — é a garantia NEGATIVA de que quem recebe não consegue mexer.

  POR QUE INSISTO NUM ITEM QUE PARECE VOCABULÁRIO
    Se o seu modelo mental é "a interface adiciona capacidade", você vai escolher
    tipo de retorno pelo motivo errado a cada assinatura que escrever daqui pra
    frente. E vai concluir o oposto do certo: vai devolver List<T> quando quiser
    "dar mais poder a quem chama", que é exatamente o que fura encapsulamento.

    A regra é: devolva o MENOS capaz que atende quem chama.

  O QUE A ESCOLHA COMPRA, concretamente, no seu NotaFiscal:

      private readonly List<ItemNota> _itens = [];      // aqui EU mexo
      public IReadOnlyList<ItemNota> Itens => _itens;   // aqui você só LÊ

    Se Itens fosse List<ItemNota>:

      nota.Autorizar();
      nota.Itens.Add(new ItemNota("Contrabando", 1m, 999999m));   // COMPILA

    AdicionarItem checa se a nota está EmDigitacao. Itens.Add não checa nada.
    A regra de negócio existiria com uma porta aberta ao lado dela.

  A SUA ÚLTIMA FRASE ESTÁ CERTA, e é a única parte que precisa ficar:
    "garante que a propriedade não será alterada por acidente."
    Guarde essa. Jogue o resto da resposta fora.

  LIMITE HONESTO: não é imutabilidade real. `(List<ItemNota>)nota.Itens`
  contorna, porque o objeto por trás continua sendo uma List. Impede ACIDENTE,
  não sabotagem — e é o que se pede de um design, não de um cofre.

  PARALELO DELPHI: é o mesmo motivo pelo qual você declara uma propriedade
  `property Itens: TEnumerable<TItem> read GetItens` em vez de expor a
  TObjectList<> direto. Você já faz isso. Só o nome da interface é novo.

2. Q11 — falta "por que um método aceita código como parâmetro"
--------------------------------------------------------------------------------

  A pergunta tinha 3 partes. Você respondeu que tipo é (delegate) e o
  equivalente Delphi. A do meio ficou sem resposta, e é a que explica o LINQ.

  A RESPOSTA
    Sort sabe ORDENAR: quicksort, particionamento, troca de elementos.
    Algoritmo genérico, escrito uma vez, testado exaustivamente pela equipe
    do .NET.

    O que Sort NÃO SABE E NÃO TEM COMO SABER é o que "maior" significa para um
    LinhaRelatorio. Por valor total? Por CNPJ alfabético? Por quantidade de
    notas? Crescente ou decrescente? Só quem chama sabe.

    Então: Sort implementa o que NÃO VARIA (o algoritmo) e recebe o que VARIA
    (o critério) como parâmetro. Isso é INVERSÃO DE CONTROLE — a biblioteca
    chama o SEU código, não o contrário.

  POR QUE AS ALTERNATIVAS SÃO PIORES
    (a) LinhaRelatorio implementar IComparable<T>: funciona, mas fixa UMA ordem
        natural no tipo. Se uma tela ordena por valor e outra por CNPJ, travou.
    (b) Escrever seu próprio laço de ordenação: reimplementar quicksort com os
        mesmos bugs de índice que todo mundo comete.

  UMA IMPRECISÃO QUE SOBROU, e ela atrapalha
    Você escreveu: "o valor retornado é uma expressão que irá executar no
    futuro, NÃO É UM VALOR DE FATO".

    A última parte está errada, e ela é o motivo pelo qual a Semana 3 confunde
    quem pensa assim. A lambda É um valor de fato: uma instância de delegate,
    um objeto no heap. Você pode guardá-la numa variável, passá-la, devolvê-la
    de um método:

        Comparison<LinhaRelatorio> porValor = (a, b) => b.ValorTotal.CompareTo(a.ValorTotal);
        linhas.Sort(porValor);       // idêntico a passar a lambda inline

    Se lambda "não fosse um valor", a linha de cima não compilaria. A parte de
    "executa no futuro" está certa: quem a invoca é o Sort, N vezes, durante a
    ordenação.

    Por que isso importa para a Semana 3: no LINQ você vai ARMAZENAR e COMPOR
    esses valores (`var filtro = ...; query.Where(filtro)`), e vai encontrar
    Expression<Func<T,bool>> — que é o delegate transformado em ÁRVORE DE DADOS
    para o EF Core traduzir em SQL. Nada disso faz sentido se lambda "não é um
    valor".

3. Q12a — a sua própria letra (c) refuta a sua letra (a)
--------------------------------------------------------------------------------

  Em (a) você escreveu:
      "é necessário deixar explícito a LIMPEZA DE MEMÓRIA"

  Em (c) você escreveu:
      "o GC automatiza A LIMPEZA DA RAM, mas transfere ao desenvolvedor
       gerenciar RECURSOS EXTERNOS"

  A (c) está certa e contradiz a (a). Você tem o modelo correto — a (a) ficou
  com a redação da primeira versão.

  Fixando: Dispose NÃO É SOBRE MEMÓRIA. A memória do StreamReader o GC recolhe
  sozinho, sem problema. O que o GC não faz é liberar o HANDLE DE ARQUIVO na
  hora certa.

      GC      -> memória gerenciada, EM ALGUM MOMENTO (não determinístico)
      Dispose -> recurso NÃO-gerenciado, AGORA (determinístico)

  Dispose é sobre TEMPO, não sobre espaço.

  Consequência prática, e é a que aparece em produção: sem Dispose, o arquivo
  fica travado até o finalizador rodar — e finalizador roda quando o GC decidir,
  que pode ser minutos depois, ou nunca, se o processo morrer antes. No Windows,
  arquivo travado significa que a próxima importação não consegue abrir.

  Sobre a sua (b): Empresa / NotaFiscal / ItemNota não dispensam `using` porque
  "são dados cuidados pela RAM". É porque NÃO IMPLEMENTAM IDisposable. E se você
  TENTAR usar `using` neles, é ERRO DE COMPILAÇÃO — não é escolha de estilo, o
  compilador te impede. Essa é a diferença mais confortável em relação ao
  Delphi: lá, esquecer o Free compila e vaza; aqui, o tipo te diz se precisa.

4. Q8 — "independente de quantos PROCESSOS" segue invertido
--------------------------------------------------------------------------------

  static é UM POR PROCESSO. Dois processos = duas cópias independentes que não
  se conhecem. O que compartilha a mesma cópia são as THREADS e as REQUISIÇÕES
  dentro do mesmo processo.

  A troca de palavra inverte a conclusão prática, e é por isso que insisto:

    Se static fosse global entre processos, um cache static funcionaria com o
    sistema escalado em 3 instâncias. Sendo POR processo, cada instância tem o
    SEU cache e eles divergem em silêncio: o usuário salva na instância 1, o
    load balancer manda a próxima requisição para a instância 2, e ele vê dado
    velho.

  A escada para guardar:

      const / static readonly imutável -> seguro sempre
      static MUTÁVEL                   -> corrompe entre REQUISIÇÕES (1 processo)
      static como cache                -> DIVERGE entre INSTÂNCIAS (N processos)

  A terceira linha é literalmente a Semana 10: cookie/antiforgery emitido numa
  instância que a outra não consegue ler, porque a chave estava em memória local.

  O que você acertou e é o mais importante: "dois usuários com duas empresas
  poderão visualizar vazamento de informações". Exato, e em sistema fiscal é
  incidente reportável.

  Faltou o segundo perigo: static ENRAÍZA o objeto. É o mesmo ponto da Q12c —
  o GC não coleta o que um campo static alcança. static Dictionary como cache
  sem expiração cresce até o processo cair.

6. Q10 — conclusão certa, mecanismo ainda ausente
--------------------------------------------------------------------------------

  "acredito que por esse motivo é nativo" é observação, não explicação. O
  mecanismo:

    DateTime NÃO é um struct com campos dia/mês/ano independentes. É um CONTADOR
    DE TICKS desde 01/01/0001. Não existe o número de ticks correspondente a 31
    de fevereiro, então o valor é IMPOSSÍVEL DE REPRESENTAR. TryParseExact não
    "consulta o calendário" — ele tenta construir o valor e não consegue.

  A diferença entre isso e uma validação: validação você pode esquecer de
  chamar. Impossibilidade de representação você não consegue burlar.

  O contraste que fecha: se o DTO guardasse a data como string, 31/02 entraria,
  atravessaria o sistema e explodiria três camadas depois — na gravação no banco
  ou num ToString de relatório, longe da origem.

  Regra: converta na fronteira, para o tipo MAIS RESTRITIVO disponível. O erro
  aparece onde nasceu.
